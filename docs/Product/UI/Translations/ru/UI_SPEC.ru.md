# UI_SPEC.ru.md — Спецификация UI / UX LacunaAuto

> **Русский перевод спецификации UI для владельца проекта.**
>
> Каноническим файлом для AI-агентов является `UI_SPEC.md`.
>
> Этот документ описывает утверждённое визуальное направление, принципы взаимодействия, адаптивность, навигацию и переиспользуемые UI-паттерны LacunaAuto.
>
> Продуктовый scope определяется `docs/Product/PRODUCT_SCOPE.md`, а технические правила работы с репозиторием — `AGENTS.md`.

Если `PRODUCT_SCOPE.md` относит функцию к future/out of scope, агент не должен реализовывать её поведение, пока отдельная продуктовая спецификация явно не перенесёт её в scope.

## 1. Общее направление дизайна

LacunaAuto использует чистый, современный, premium-style интерфейс автомобильного marketplace.

Утверждённое направление:

- светлый и просторный интерфейс;
- крупные качественные фотографии автомобилей;
- сильная чёрная типографика;
- яркий оранжево-красный акцент;
- скруглённые карточки и элементы управления;
- минимум визуального шума;
- удобная touch-навигация;
- простая и ясная иерархия информации;
- современный автомобильный характер без перегруженности.

Интерфейс должен ощущаться скорее как современное consumer mobile marketplace-приложение, чем как традиционный плотный сайт объявлений.

### 1.1 Ключевые визуальные характеристики

- современный;
- premium;
- automotive;
- минималистичный;
- чистый;
- photo-first;
- быстрый;
- дружелюбный;
- контрастный;
- mobile-first.

## 2. Приоритет платформ

### 2.1 Основной приоритет — телефон

UI проектируется **mobile-first**.

Основной диапазон ширины:

- 360–430 CSS px для типичных телефонов;
- интерфейс должен корректно работать и вне этого диапазона;
- нельзя привязывать layout к одному конкретному разрешению телефона.

Основная мобильная форма приложения:

- **.NET MAUI Blazor Hybrid** для Android/iOS/Windows после добавления Hybrid-проекта;
- Razor UI по возможности переиспользуется с web;
- в Hybrid UI отображается через `BlazorWebView`.

### 2.2 Web / PWA

Web-версия использует **Blazor WebAssembly / PWA**.

Desktop web — это вторичное представление того же продукта и той же дизайн-системы, а не отдельный продукт.

На desktop те же компоненты могут перестраиваться:

- нижняя мобильная навигация → верхнее меню / sidebar;
- одна колонка → grid / split layout;
- полноэкранные mobile-фильтры → постоянная левая панель;
- вертикальная mobile detail page → разделение gallery/details по колонкам.

Не создавать отдельный несвязанный desktop-дизайн.

## 3. Design Tokens

Конкретные значения можно немного подстроить во время реализации, но общая визуальная система должна сохраняться.

### 3.1 Цвета

| Token | Рекомендуемое значение | Назначение |
|---|---:|---|
| `--color-accent` | `#FF5A00` | Главные CTA, активная навигация, выбранные фильтры |
| `--color-accent-hover` | `#E84F00` | Hover/pressed состояние |
| `--color-text-primary` | `#111111` | Заголовки, цены, основной текст |
| `--color-text-secondary` | `#687280` | Метаданные |
| `--color-text-muted` | `#9AA2B1` | Placeholder / второстепенные данные |
| `--color-background` | `#FFFFFF` | Основные поверхности |
| `--color-background-soft` | `#F5F6F8` | Фон приложения / вторичные поверхности |
| `--color-border` | `#E5E7EB` | Разделители и границы |
| `--color-dark-action` | `#101012` | Чёрные primary-кнопки / floating action |
| `--color-error` | token реализации | Ошибки |
| `--color-success` | token реализации | Успешные состояния |

Не добавлять несколько конкурирующих brand-цветов.

### 3.2 Типографика

Предпочтение:

- современный sans-serif;
- системный/native font stack подходит и предпочтителен на первом этапе;
- иерархия создаётся размером и весом, а не декоративными шрифтами.

Ориентировочная шкала:

| Роль | Вес | Размер |
|---|---:|---:|
| Display / hero | 700 | 32–40 px |
| H1 | 700 | 28–32 px |
| H2 | 600–700 | 22–26 px |
| H3 | 600 | 18–20 px |
| Основной текст | 400 | 14–16 px |
| Метаданные | 400–500 | 12–14 px |
| Label / chip | 500–600 | 12–14 px |
| Цена | 700 | 24–34 px |

### 3.3 Скругления

Использовать скругления последовательно:

- небольшие controls/chips: 12–16 px;
- карточки: 20–24 px;
- крупные изображения: 24–28 px;
- pill-кнопки: 999 px;
- bottom sheets: 28–36 px сверху;
- центральная floating-кнопка: круглая.

### 3.4 Отступы

Основной ритм — кратный примерно 8 px:

- 4 px — micro;
- 8 px — tight;
- 12 px — icon/text;
- 16 px — стандартный mobile;
- 20–24 px — секции;
- 32 px — крупное разделение.

Горизонтальный padding mobile page: примерно **16–20 px**.

### 3.5 Тени

Тени использовать умеренно:

- floating CTA;
- price badge;
- floating bottom navigation;
- overlays/sheets;
- выделенные карточки.

Не делать сильную тень у каждой карточки.

## 4. Application Shell — Mobile

### 4.1 Верхняя область

Главная/feed содержит:

- логотип LacunaAuto;
- вход в поиск;
- кнопку фильтра;
- profile/avatar только когда account functionality входит в scope.

### 4.2 Основной поиск

Поиск должен быть заметнее, чем просто круглая иконка лупы.

Предпочтительно:

- компактное поле поиска или разворачиваемый search control;
- placeholder `Search make, model, keyword…`;
- рядом отдельная кнопка фильтра;
- фильтр может показывать badge количества активных фильтров.

На первом этапе поиск может просто открывать страницу listings/search.

### 4.3 Быстрые категории

Горизонтально прокручиваемые chips:

- All Vehicles
- Electric
- SUVs
- Sports
- Sedans
- Trucks

Активный chip — accent; остальные — светлые с тонкой границей.

Категории являются shortcut, но не заменяют полноценные фильтры.

### 4.4 Нижняя навигация

Утверждённая долгосрочная схема:

1. **Feed / Home**
2. **Search**
3. **Sell** — центральный `+`
4. **Saved**
5. **Profile**

В текущем MVP активируются только пункты, разрешённые `PRODUCT_SCOPE.md`.

`Inbox` не должен занимать постоянное место, пока messaging реально не вошёл в scope.

### 4.5 Центральная кнопка Sell

Центральный круглый `+` означает **Sell Vehicle**.

Визуально:

- чёрный круг;
- белый плюс;
- слегка поднят над bottom navigation;
- большой touch target;
- лёгкая тень.

Поведение не реализуется, пока создание объявления не будет включено в product scope.

### 4.6 Safe Areas

Hybrid/mobile должен учитывать:

- Android navigation area;
- iOS safe area;
- notch/status bar;
- появление клавиатуры.

## 5. Home / Feed

### 5.1 Назначение

Главная — discovery-first точка входа.

Основные цели:

1. быстрый поиск;
2. быстрый выбор категории;
3. привлекательный просмотр объявлений;
4. переход к деталям автомобиля.

### 5.2 Порядок блоков

1. header/logo;
2. search + filters;
3. category chips;
4. optional section/result title;
5. cards;
6. bottom navigation.

### 5.3 Feed

Основной discovery-режим использует **крупные photo-first карточки**.

Позже можно добавить compact/grid mode для быстрого просмотра большого количества машин.

### 5.4 Карточка объявления

Минимум:

- главное фото;
- марка;
- модель/комплектация;
- цена;
- год;
- пробег;
- город/локация, если полезно;
- ещё одна важная характеристика при наличии места — fuel/powertrain или transmission;
- save/favorite только когда функция в scope.

Иерархия:

1. Фото
2. Марка — небольшой secondary текст
3. Модель/trim — сильный текст
4. Цена
5. Год + пробег + optional third characteristic

Возможные badges:

- Just Added
- Electric
- Featured
- Dealer

Badge показывается только при реальном состоянии данных.

### 5.5 Цена

Цена должна быть видна сразу.

Оранжевый блок/badge допустим, но:

- не перекрывает важную часть фото;
- остаётся читаемым;
- не подавляет название автомобиля.

### 5.6 Нажатие

Нажатие на любую основную область карточки открывает детали.

Favorite control, если присутствует, имеет отдельный tap target.

## 6. Search / Listings

### 6.1 Назначение

Listings оптимизирован для целевого поиска, в отличие от discovery-feed.

### 6.2 Mobile layout

Рекомендуется:

- компактный top bar;
- количество результатов;
- sort;
- search field;
- filter entry;
- результаты одной компактной колонкой или двумя колонками, если ширина позволяет.

На узких устройствах предпочтительна одна колонка.

### 6.3 Сортировка

Возможные варианты:

- Newest
- Price low to high
- Price high to low
- Mileage
- Year

Показывать только поддерживаемые backend/API варианты.

### 6.4 Большие списки

- pagination / incremental loading;
- skeleton loading;
- без disruptive full-page spinner;
- по возможности сохранять scroll/filter state при возврате из details.

## 7. Фильтры

### 7.1 Mobile presentation

Для ожидаемого количества автомобильных параметров предпочтителен **полноэкранный filter panel**.

### 7.2 Фильтры

Вероятный initial set:

- Location
- Make
- Model
- Price
- Year
- Mileage
- Fuel
- Transmission
- Body type

Добавлять постепенно по мере поддержки backend.

### 7.3 Controls

- searchable dropdown/select для make/model/location;
- min/max или range controls для чисел;
- chips/segmented controls для небольшого количества вариантов;
- searchable list для длинных справочников.

### 7.4 Actions

Фильтры содержат:

- Close/back;
- Reset/Clear;
- primary `Show N vehicles`.

Если backend ещё не умеет считать результат — `Show results`.

### 7.5 Активные фильтры

После применения:

- badge количества на filter button;
- важные активные фильтры могут отображаться removable chips.

## 8. Vehicle Details

### 8.1 Назначение

Страница должна дать достаточно информации, чтобы пользователь решил, интересен ли автомобиль и стоит ли связываться с продавцом.

### 8.2 Mobile order

1. gallery;
2. back;
3. save/share, когда поддерживается;
4. make;
5. model/trim;
6. price;
7. location / listing age;
8. quick facts;
9. description;
10. extended specs;
11. seller/contact;
12. CTA контакта.

### 8.3 Gallery

- horizontal swipe;
- position indicator;
- full-screen gallery по tap, когда реализована;
- корректный aspect ratio;
- skeleton/placeholder;
- отсутствие layout jumps.

### 8.4 Quick Facts

Например:

- Year
- Mileage
- Transmission
- Fuel / powertrain

### 8.5 Description

Для длинного текста:

- `Read more`;
- inline expand или details section;
- данные не должны теряться из-за truncation.

### 8.6 Contact CTA

Предпочтительные будущие действия:

- **Contact Seller / Message Seller**
- **Call Seller**

`Make Offer` не является default MVP action и появляется только после отдельного продуктового решения.

В текущем MVP допустим placeholder/static contact block.

## 9. Sell Vehicle — будущая функция

Визуальное направление формы утверждено, но создание объявления пока вне initial MVP.

Когда функция войдёт в scope, использовать многошаговый flow:

1. Vehicle / VIN
2. Basic details
3. Specifications / condition
4. Photos
5. Price
6. Seller/contact
7. Preview
8. Publish

Правила:

- один primary action на экран;
- большие touch targets;
- draft/autosave по возможности;
- progress indication;
- camera/gallery может быть Hybrid-specific;
- validation рядом с полем;
- введённые данные не должны теряться при навигации.

## 10. Saved / Profile / Messaging — будущие функции

Эти элементы входят в долгосрочный visual design, но не автоматически в текущую реализацию.

### Saved

- переиспользовать те же listing cards;
- полезный empty state;
- мгновенная визуальная реакция на Save.

### Profile

Будущие блоки:

- account basics;
- own listings;
- settings;
- sign in/out;
- seller identity.

### Messaging

Не помещать messaging в primary nav, пока функции реально нет.

## 11. Состояния

Каждый data-driven экран должен иметь:

### Loading

Skeleton placeholders, похожие по форме на конечный контент.

### Empty

Короткое объяснение + полезное действие, например `Clear filters`.

### Error

Короткое сообщение + `Retry`.  
Не показывать raw exception.

### Offline

Для PWA и mobile Hybrid:

- понятный connectivity state;
- не показывать ложный успех операции без соединения.

---

## 12. Interaction Rules

### Touch targets

Обычно не менее **44×44 CSS px**.

### Feedback

Нужны состояния:

- pressed;
- disabled;
- selected;
- loading.

### Navigation

- back по возможности сохраняет context;
- карточка быстро и предсказуемо открывает details;
- минимум лишней анимации.

### Pull to refresh

Допустим для mobile feed/results, но не должен быть единственным способом обновления.

## 13. Desktop / Tablet

Desktop вторичен, но должен выглядеть законченным.

### Breakpoints

Ориентировочно:

- Mobile `< 768 px`
- Tablet `768–1023 px`
- Desktop `>= 1024 px`

### Desktop Home

- top navigation;
- более крупный hero/search;
- видимое search field;
- popular categories;
- grid featured/recent vehicles.

### Desktop Listings

- filter sidebar слева;
- result count + sort сверху;
- 2–4 columns;
- без mobile bottom nav.

### Desktop Details

- крупная gallery;
- price/facts/contact рядом;
- подробности ниже;
- CTA заметный, но ненавязчивый.

## 15. Web vs Hybrid

### Общее

По возможности shared:

- layout markup;
- cards;
- typography;
- colors;
- filters;
- listing details;
- form controls;
- loading/empty/error states.

### Только Hybrid при необходимости

- native camera/photo picker;
- share sheet;
- permissions;
- push notifications;
- deep links;
- platform safe-area особенности.

### Только Web/PWA при необходимости

- install/PWA prompts;
- SEO/public URL behavior;
- browser sharing fallback;
- desktop hover.

Не дублировать целые экраны без реальной platform-specific причины.

## 16. Accessibility

Минимум:

- достаточный contrast;
- keyboard navigation на web;
- focus states;
- semantic buttons/links;
- alt text;
- form labels;
- иконки не являются единственным носителем смысла;
- состояние не передаётся только цветом.

---

## 17. Performance

Фотографии автомобилей — главный performance risk.

Требования:

- responsive image sizes;
- lazy loading;
- резервирование размеров изображения;
- thumbnails в списке;
- full-resolution только по необходимости;
- skeletons;
- pagination/virtualization для длинных списков.

## 18. Локализация, региональное форматирование и валюта

LacunaAuto должен поддерживать интернационализацию с самого начала разработки UI.

Приложение должно рассматривать следующие параметры как **три полностью независимые пользовательские настройки**:

1. **Язык приложения** — определяет язык пользовательского интерфейса.
2. **Региональный формат** — определяет формат дат, времени, чисел, десятичных и групповых разделителей и т.п.
3. **Валюта** — определяет предпочтительную валюту пользователя для денежных значений там, где поддерживается отображение/конвертация валют.

Изменение одной настройки **не должно автоматически изменять две другие**.

Примеры корректных комбинаций:

- русский UI + польский региональный формат + PLN;
- украинский UI + украинский региональный формат + USD;
- английский UI + польский региональный формат + EUR.

### 18.1 Язык приложения

Поддерживаемые языки интерфейса:

- English (`en`) — язык по умолчанию и fallback;
- Ukrainian (`uk`);
- Russian (`ru`).

Требования:

- Весь пользовательский текст приложения должен быть локализуемым.
- Нельзя hard-code пользовательские строки непосредственно в Razor components, pages, dialogs, validation messages, navigation items, buttons, placeholders, empty states, error states или notifications.
- Использовать стандартный механизм локализации .NET (`IStringLocalizer` / `.resx`), если позже в проекте не будет утверждён другой подход.
- Shared Razor components должны по возможности использовать одни и те же localization resources в Web/PWA и .NET MAUI Blazor Hybrid.
- Если перевод отсутствует, использовать English как fallback.
- Layout должен выдерживать разную длину переводов без обрезания, наложения и разрушения выравнивания.
- Нельзя проектировать controls под фиксированную ширину английских подписей.
- Описания автомобилей и другой пользовательский контент не должны переводиться автоматически, если это явно не предусмотрено отдельной продуктовой функцией.

### 18.2 Региональный формат

Региональный формат — это **одна пользовательская настройка**, которая определяет culture-dependent представление:

- даты;
- времени;
- десятичного разделителя;
- разделителя групп/тысяч;
- числового форматирования;
- других culture-sensitive значений, где это уместно.

Пользователю не нужны отдельные настройки для формата даты, формата чисел, разделителей и т.п. Всё выбирается одновременно одним regional-format culture/preset.

Примеры regional-format presets:

- English (United States)
- English (United Kingdom)
- Ukrainian (Ukraine)
- Russian
- Polish (Poland)

Точный список поддерживаемых региональных preset'ов может расширяться независимо от списка языков интерфейса.

Требования:

- Региональный формат должен быть независим от языка приложения.
- Изменение языка приложения не должно перезаписывать явно выбранный пользователем региональный формат.
- Даты и числа должны форматироваться с использованием выбранного регионального формата.
- Не следует вручную форматировать culture-sensitive значения, если можно использовать стандартное culture-aware форматирование .NET.
- Региональный формат не должен определять выбранную валюту.

### 18.3 Валюта

Валюта — отдельная независимая пользовательская настройка.

Требования:

- Пользователь должен иметь возможность выбрать предпочтительную валюту независимо от языка приложения и регионального формата.
- Внутри приложения использовать ISO 4217 currency codes там, где это уместно, например `USD`, `EUR`, `PLN`, `UAH`.
- Список поддерживаемых валют должен быть расширяемым/настраиваемым и не должен выводиться из списка языков интерфейса.
- Отображение денежных значений должно учитывать выбранную валюту и выбранный региональный формат там, где это уместно.
- Изменение валюты не меняет язык приложения или региональный формат.
- Изменение регионального формата не меняет валюту.
- Нельзя предполагать, что русскоязычный пользователь хочет RUB, украиноязычный — UAH, а англоязычный — USD.

Конвертация валют, источник exchange rates, исходная валюта объявления, правила округления и способ отображения исходной и конвертированной цены являются отдельными продуктовыми и бизнес-требованиями и должны быть описаны до реализации. Архитектура UI не должна затруднять добавление этих правил позже.

### 18.4 Начальная инициализация настроек

При первом запуске приложение может использовать настройки устройства/браузера для выбора разумных начальных значений:

- Язык приложения: поддерживаемый язык устройства/браузера, иначе English.
- Региональный формат: региональная культура устройства/браузера, если поддерживается, иначе настроенное значение по умолчанию.
- Валюта: регионально подходящая валюта, если она поддерживается, иначе product default currency.

Это только **начальные значения**.

После того как пользователь явно изменил настройку, его выбор имеет приоритет над автоматическим определением.

### 18.5 Сохранение настроек

Все три настройки должны сохраняться независимо между запусками приложения:

- Язык приложения
- Региональный формат
- Валюта

Для анонимного пользователя на первом этапе достаточно локального client storage.

После появления авторизации настройки можно дополнительно хранить на сервере и синхронизировать между устройствами, но это не требуется для initial anonymous experience.

### 18.6 UI настроек

В settings/profile области приложения должны быть три отдельные настройки:

- **Language / Язык**
- **Regional format / Региональный формат**
- **Currency / Валюта**

Каждая показывает текущее выбранное значение и может быть изменена независимо от остальных.

По возможности изменения должны применяться сразу, без перезапуска приложения.

### 18.7 Рекомендации по реализации

Инфраструктуру интернационализации следует вводить вместе с первыми UI-компонентами, а не добавлять задним числом.

AI-агенты при реализации UI должны:

1. использовать localization resources для всех новых пользовательских строк;
2. добавлять переводы на English, Ukrainian и Russian при добавлении нового UI-текста;
3. сохранять English как translation fallback;
4. хранить Language, Regional Format и Currency как три отдельных preference values;
5. никогда не делать одну настройку постоянной производной от другой;
6. не дублировать локализованные строки между компонентами, если уместен общий resource;
7. проверять UI с более длинными переводами;
8. использовать culture-aware API .NET для дат и чисел;
9. не закладывать hard-coded currency assumptions в переиспользуемые UI-компоненты.

## 19. Правила для AI-агентов

При реализации UI:

1. Прочитать `AGENTS.md`.
2. Прочитать `docs/Product/PRODUCT_SCOPE.md`.
3. Прочитать канонический `UI_SPEC.md`.
4. Прочитать screen/feature spec, если существует.
5. Не считать future feature текущей только потому, что она визуально описана.
6. Переиспользовать компоненты и tokens.
7. Не создавать новую дизайн-систему для одного экрана.
8. Следовать conventions проекта по CSS isolation/shared styles.
9. Не держать сложную логику в markup.
10. Реализовывать loading/empty/error states.
11. Сохранять mobile-first.
12. Не рефакторить несвязанный UI.

## 20. Отдельные screen specs

По мере роста продукта детали экранов выносятся отдельно:

```text
docs/Product/UI/UI_SPEC.md
docs/Product/Screens/MainLayout.md
docs/Product/Screens/HomePage.md
docs/Product/Screens/ListingsPage.md
docs/Product/Screens/Filters.md
docs/Product/Screens/ListingDetailsPage.md
docs/Product/Screens/SellVehicle.md        # когда функция войдёт в scope
docs/Product/Features/*.md
```

`UI_SPEC.md` остаётся глобальной design system / UX contract.

Screen files описывают конкретный экран.

Feature files описывают поведение, затрагивающее несколько экранов или UI/backend.

## 21. Утверждённый итог

Базовое направление LacunaAuto:

- mobile-first;
- крупные фото автомобилей;
- белый/soft-gray интерфейс;
- чёрная типографика;
- orange-red accent;

- быстрые категории;

- большая gallery на details;
- простые quick facts;
- сильный seller contact CTA;
- центральный Sell action после включения listing creation в scope;

- desktop строится из той же дизайн-системы, а не проектируется независимо.
