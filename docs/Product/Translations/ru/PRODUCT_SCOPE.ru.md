## 1. Видение продукта

LacunaAuto — это современная платформа для поиска и размещения объявлений о продаже транспортных средств.

Продукт должен позволять пользователям просматривать, искать, фильтровать и открывать объявления об автомобилях в удобном веб-интерфейсе. Со временем платформа может поддерживать размещение объявлений, аккаунты пользователей, избранное, профили дилеров, модерацию, мобильное приложение и дополнительные автомобильные сервисы.

Первая цель — построить маленькое, но реально работающее ядро продукта: пользователь открывает приложение, находит подходящие автомобили и просматривает детали объявления.

---

## 2. Тип продукта

LacunaAuto — это автоагрегатор / classifieds-платформа для транспортных объявлений.

На начальном этапе продукт не является:

- полноценной CRM для автодилеров;
- платёжной платформой;
- сервисом проверки истории автомобиля;
- маркетплейсом кредитования или страхования;
- chat-first маркетплейсом;
- сложной аукционной платформой.

Эти направления могут быть добавлены позже только после явного включения в scope.

---

## 3. Целевые пользователи

### 3.1 Покупатели автомобилей

Пользователи, которые хотят искать автомобили, сравнивать объявления, использовать фильтры и открывать детали объявлений.

### 3.2 Частные продавцы — будущий scope

Пользователи, которые хотят создавать и управлять собственными объявлениями.

### 3.3 Дилеры — будущий scope

Профессиональные продавцы, которые могут управлять множеством объявлений и иметь публичные профили.

### 3.4 Администраторы / модераторы — будущий scope

Внутренние пользователи, которые проверяют объявления, обрабатывают жалобы и следят за качеством платформы.

---

## 4. Начальный MVP Scope

Начальный MVP фокусируется на просмотре и поиске объявлений.

Пользователь должен иметь возможность:

1. Открыть главную страницу приложения.
2. Увидеть понятный вход в поиск автомобилей.
3. Открыть страницу списка объявлений.
4. Просматривать список/сетку объявлений.
5. Видеть основную информацию об автомобиле в карточке объявления.
6. Фильтровать объявления по главным параметрам.
7. Открыть страницу деталей объявления.
8. Посмотреть подробную информацию о выбранном автомобиле.
9. Увидеть контактную информацию продавца или placeholder-блок контактов.

В начале MVP может использовать seed/mock данные, но реализация должна постепенно перейти к реальным backend-данным через API и базу данных.

---

## 5. Что не входит в начальный MVP

Следующие функции намеренно не входят в первый MVP, если они явно не будут перенесены в scope:

- регистрация и login пользователей;
- создание, редактирование или удаление объявлений через UI;
- загрузка фотографий;
- избранное / сохранённые объявления;
- профили пользователей;
- профили дилеров;
- сообщения / чат;
- платежи или продвигаемые объявления;
- продвинутая модерация;
- админ-панель;
- уведомления;
- многоязычный UI;
- полноценное native mobile приложение;
- сложная SEO-стратегия и публичная индексация;
- интеграция с историей автомобиля;
- интеграции с кредитованием, страхованием или лизингом.

Authentication может появиться позже как пункт навигации или placeholder только если это будет явно указано в feature specification.

## 6. Основные пользовательские сценарии

### 6.1 Просмотр объявлений

Как покупатель автомобиля, я хочу открыть страницу объявлений и увидеть доступные автомобили, чтобы начать сравнение.

### 6.2 Фильтрация объявлений

Как покупатель автомобиля, я хочу фильтровать объявления по основным характеристикам, чтобы быстрее найти подходящие варианты.

Начальные фильтры могут включать:

- марка;
- модель;
- диапазон цены;
- диапазон года выпуска;
- диапазон пробега;
- тип топлива;
- коробка передач;
- тип кузова;
- локация.

Фильтры должны добавляться постепенно. Первая реализация может содержать только часть из них.

### 6.3 Просмотр деталей объявления

Как покупатель автомобиля, я хочу открыть объявление и увидеть подробную информацию, чтобы понять, интересен ли мне этот автомобиль.

### 6.4 Контакт с продавцом

Как покупатель автомобиля, я хочу увидеть контактную информацию продавца или понятный контактный блок, чтобы понимать, что делать дальше.

В первом MVP это может быть простой placeholder или статические контактные данные.

## 7. Начальные экраны продукта

Детальное поведение каждого экрана при необходимости должно находиться в отдельных файлах `docs/Product/Screens/`.

Начальные экраны:

1. **Главная страница**
   - объясняет продукт;
   - даёт вход в поиск/просмотр объявлений;
   - позже может показывать избранные или свежие объявления.

2. **Страница объявлений**
   - показывает карточки автомобилей;
   - поддерживает базовые фильтры;
   - обрабатывает состояния загрузки, пустого списка и ошибки.

3. **Страница деталей объявления**
   - показывает полные детали автомобиля;
   - показывает изображения или placeholders;
   - показывает блок продавца/контакта;
   - позволяет вернуться к списку объявлений.

4. **Главный layout / навигация**
   - даёт стабильную структуру навигации;
   - в первом MVP должен оставаться простым;
   - login/account navigation не входит в первый MVP, если явно не добавлен.

## 8. Начальные продуктовые данные

Детальная доменная модель при необходимости должна находиться в `docs/Product/DomainModel.md`.

Продукту, скорее всего, понадобятся следующие понятия:

- объявление автомобиля;
- марка автомобиля;
- модель автомобиля;
- цена;
- год выпуска;
- пробег;
- тип топлива;
- тип коробки передач;
- тип кузова;
- информация о двигателе;
- локация;
- информация о продавце/контактах;
- фотографии автомобиля.

Для первой реализации модель должна оставаться простой. Не нужно заранее усложнять её под будущие сценарии.

## 9. Продуктовые модули

### 9.1 Просмотр объявлений — начальный MVP

Базовый просмотр, список/сетка объявлений, простая фильтрация и страница деталей.

### 9.2 Управление объявлениями — будущий scope

Создание, редактирование, публикация и удаление объявлений.

### 9.3 Authentication и аккаунты — будущий scope

Login, регистрация, управление аккаунтом, идентичность продавца и access control.

### 9.4 Избранное — будущий scope

Сохранение объявлений для последующего сравнения.

### 9.5 Профили дилеров — будущий scope

Страницы дилеров, управление объявлениями дилера и данные дилера.

### 9.6 Модерация / администрирование — будущий scope

Проверка, одобрение, отклонение, скрытие объявлений и обработка жалоб.

### 9.7 Mobile / Hybrid приложение — будущий scope

Blazor Hybrid / MAUI приложение с максимальным переиспользованием shared UI компонентов.

## 10. Принципы поведения продукта

- Первый пользовательский опыт должен быть простым и быстрым.
- Лучше рабочий vertical slice, чем большая незавершённая архитектура.
- Не добавлять продуктовые функции только потому, что архитектура уже позволяет это сделать.
- Не реализовывать будущие модули, пока они явно не перенесены в scope.
- UI должен показывать только то поведение, которое реально поддержано, либо явно обозначено как placeholder.
- Каждая новая feature должна сначала обновлять соответствующую продуктовую документацию, а уже потом реализовываться.

## 11. Правила документации

Этот файл является верхнеуровневым документом product scope.

Для деталей используем дополнительные файлы:

```text

/docs/Product/DomainModel.md             # Продуктовые/доменные понятия и сущности
/docs/Product/Screens/*.md               # Поведение конкретных экранов
/docs/Product/Features/*.md              # Поведение конкретных features
/docs/Product/Roadmap.md                 # Опциональное планирование будущего
```

Не нужно помещать сюда детальное UI-поведение, API-контракты, схему базы данных или implementation details, если они не определяют product scope.

---

## 12. Управление изменениями

При добавлении новой feature:

1. Определить, меняет ли она product scope.
2. Если да — обновить этот файл.
3. Добавить или обновить feature specification в `docs/Product/Features/`.
4. Добавить или обновить screen specification в `docs/Product/Screens/`, если меняется UI-поведение.
5. Только после этого реализовывать feature.

AI-агенты не должны незаметно расширять product scope во время реализации кода.

---

## 13. Текущий snapshot продуктовых решений

Текущее согласованное направление:

- Начать с просмотра объявлений автомобилей.
- Сначала сделать базовый UI, при необходимости на mock/seed данных.
- Затем добавить минимальный backend vertical slice для объявлений.
- Затем подключить Blazor UI к реальному API.
- Authentication, создание объявлений, избранное, чат, платежи и админка не входят в первый MVP.
